## 先探索，再规划，最后编码

将研究/规划与实现分离，避免解决错误的问题。推荐四阶段工作流：

**1. 探索** — 进入 Plan 模式（`Shift+Tab`），Claude 只读取文件、回答问题，不修改代码。

```
阅读 /src/auth 目录，理解我们如何处理 session 和登录。
也看看环境变量管理密钥的方式。
```

**2. 规划** — 让 Claude 创建详细的实现计划。

```
我想添加 Google OAuth。需要修改哪些文件？
Session 流程是怎样的？创建一个计划。
```

**3. 实现** — 切回正常模式，让 Claude 按计划编码。

```
按照你的计划实现 OAuth 流程。为回调处理器编写测试，
运行测试套件并修复所有失败。
```

**4. 提交** — 让 Claude 提交并创建 PR。

```
用描述性的消息提交，然后打开一个 PR
```

<Callout>
如果任务范围清晰、改动很小（修复拼写、添加日志、重命名变量），跳过规划直接做。当你能用一句话描述 diff 时，不需要计划。
</Callout>

## 提供验证方式

给 Claude 提供测试、截图或预期输出来验证工作——这是**最高杠杆**的实践。

| 策略 | 模糊版本 | 精确版本 |
|------|----------|----------|
| 提供验证标准 | "实现一个验证邮箱的函数" | "写一个 validateEmail 函数。测试用例：user@example.com 为 true，invalid 为 false。实现后运行测试" |
| 视觉验证 UI | "让仪表盘好看点" | "[贴截图] 实现这个设计，截图比较差异并修复" |
| 定位根因 | "构建失败了" | "构建因这个错误失败：[贴错误]。修复它并验证构建成功，解决根因而不是压制错误" |

## 管理上下文窗口

上下文质量在 20–40% 容量时就开始下降，而非 100%。

- 不相关任务之间积极使用 `/clear` 清除上下文
- 使用 `/compact` 压缩历史，但全新会话通常更好
- 一次对话聚焦一个功能或任务，防止上下文交叉污染
- 连续纠正 Claude 超过两次后，执行 `/clear` 并写一个更好的初始提示
- 在 CLAUDE.md 中定制压缩行为：`"压缩时，始终保留完整的已修改文件列表和测试命令"`

## 让 Claude 采访你

对于大型功能，先让 Claude 反过来采访你：

```
我想构建 [简要描述]。用 AskUserQuestion 工具详细采访我。

问关于技术实现、UI/UX、边界情况、关注点和权衡的问题。
不要问显而易见的问题，深入我可能没考虑到的困难部分。

持续采访直到覆盖所有方面，然后写一个完整的规格到 SPEC.md。
```

规格完成后，**开一个新会话**来执行——新会话有干净的上下文专注于实现。

## 提示词技巧

使用"深度思考"关键词触发更深层推理：

| 关键词 | 效果 |
|--------|------|
| `think` | 标准思考 |
| `think hard` | 深度思考 |
| `think harder` | 更深度思考 |
| `ultrathink` | 最深度思考（消耗更多 token） |

## 常见反模式

| 反模式 | 症状 | 解决方案 |
|--------|------|----------|
| 厨房水槽会话 | 一个会话处理多个不相关任务，上下文充满无关信息 | 任务间使用 `/clear` |
| 反复纠正 | 纠正 Claude 超过两次仍然错误 | `/clear` 后用更好的初始提示重新开始 |
| 过长的 CLAUDE.md | 指令太多，Claude 忽略一半 | 精简到 300 行以内，无效规则删除或转为 Hook |
| 先信任后验证 | Claude 产出看似正确但缺少边界处理的代码 | 始终提供验证方式（测试、脚本、截图） |
| 无限探索 | 让 Claude "调查"但不限定范围，读取数百文件填满上下文 | 缩小调查范围或使用子代理 |
