演进：从 .cursorrules 到 .mdc

阶段文件位置特点
早期.cursorrules项目根目录单文件，所有规则混在一起
现在.mdc 文件.cursor/rules/ 目录多文件模块化，支持条件触发

.cursorrules 仍然兼容，但推荐迁移到 .cursor/rules/ 目录下的 .mdc 文件，获得更好的模块化和条件触发能力。

.mdc 文件结构

每个 .mdc 文件包含 YAML frontmatter 和 Markdown 正文：

Frontmatter 字段

字段类型说明
descriptionstring规则描述，帮助 AI 判断是否应用此规则
globsstring文件匹配模式，决定 AutoAttach 的触发范围
alwaysApplyboolean是否始终注入上下文

四种规则类型

根据 alwaysApply 和 globs 的组合，规则分为四种触发方式：

Always（始终生效）

每次对话都自动注入。适合全局性规范，如项目技术栈、通用编码风格。

AutoAttach（自动附加）

当对话引用了匹配 glob 的文件时自动触发。适合特定文件类型的规范，如测试规范、API 路由规范。

Agent Request（AI 按需）

AI 根据 description 自行判断是否需要此规则。适合特定场景的指南，如数据库迁移步骤。

Manual（手动引用）

需要在对话中通过 @ruleName 显式引用。适合偶尔使用的参考资料。

文件组织

推荐使用数字前缀控制优先级：

编写原则

原则说明
控制篇幅单个规则文件不超过 500 行，过长则拆分
给出示例每条规则附带正确和错误的代码示例
具体明确"使用 interface" 优于 "使用合适的类型定义方式"
标记废弃对不再使用的模式明确标注 @deprecated
定期维护随框架升级和团队实践演进及时更新
团队共享.cursor/rules/ 提交到 Git，团队统一标准

注意

规则过多反而会降低 AI 表现——上下文窗口被规则占满，留给实际代码的空间就少了。只保留真正必要的规则，删除不再适用的旧规则。

上下文管理

用 @ 符号精准引用、Notepads 持久化信息、上下文窗口管理策略与提示词技巧。

工作流最佳实践

Plan Mode 规划驱动、Composer 多文件编辑、Debug 调试与 Agent Review 代码审查。
